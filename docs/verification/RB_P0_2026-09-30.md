## 2. §4 设计系统落地

### 2.1 三层令牌（唯一来源）

`packages/config/tokens/theme.css`（约 605 行）是**唯一令牌来源**，分三层：

1. **primitive 层**：色板原始值（明黄/天蓝/草绿、中性灰阶、靛蓝），不参与组件消费；
2. **semantic 层**：`--background` / `--foreground` / `--primary` / `--surface-sunken` / `--border-strong` / `--danger` 等语义别名；
3. **component 层**：`--tap-min` / `--kmap-node` / `--mastery-bar-height` / `--text-app*` / `--radius-*` 等组件级契约。

`packages/config/tokens/palette.cjs` 是同一套值的 JS 镜像，供 Storybook/Ladle 与单测直接读取，保证「设计稿 = 代码 = 断言」三者同源。

### 2.2 双主题皮肤（方案A「学院派骨架 + 双主题皮肤」）

- **骨架统一**：信息架构与 8pt 网格三端一致；皮肤只换令牌值。
- **儿童主题（`kids`）**：圆角 ≥12px、明黄/天蓝/草绿、18px 字号基准、点击热区 ≥48px；**不提供深色**。
- **少年/成人主题（`focus`）**：圆角 6px、中性灰底 + 靛蓝、14px 字号基准；深色为可选（`.dark`）。
- 主题切换在 `apps/desktop/src/routes/onboarding.tsx` 选学段时自动完成，并写入用户画像。

**关键实现约束（已踩坑，勿回退）**：

- CSS 自定义属性 `var()` **在声明处求值并随继承传递** ⇒ 字阶与圆角必须在**每个主题块内**落具体像素（`--type-*` / `--r-*`），不能只在一处定义。Tailwind utility 别名也必须声明进主题块本身。
- `[data-theme="kids"]` 置于皮肤块**最后**，靠源序覆盖 `.dark`，实现「儿童主题无深色」。
- `tailwind-merge` 会把未知 `text-` 前缀归入 `text-color` 组 ⇒ `text-app-*` 必须用 `extendTailwindMerge` 注册进 `font-size` 组，否则类名互相覆盖。
- Ladle 5.1.1 的 `.ladle/components.tsx` **只能 `export const`**（出现 `export type` / `export function` 会导致全站白屏）。

### 2.3 Tailwind v4 管线

`packages/ui` 走 Tailwind v4：`postcss.config.mjs` + `src/styles.css`（`@import` 令牌 + `@theme` 映射）。三端（desktop / web / mobile）共用同一份令牌与管线，无重复实现（§8 约束 7）。

归因结论：

1. **主因是环境**：CPU 基准指数下降 21%，而 TBT 是 CPU 密集指标；同批次机器上还并行运行 Docker 多容器与用户浏览器进程。
2. **次因是 P0 引入的载荷**：CSS +3.2 KiB 是双主题令牌的必要成本（绝对值仍仅 7.7 KiB），JS +5.1 KiB；合计 +9.5%，不足以单独解释 TBT 翻三倍。
3. **run 间方差极大**（performance 0.81~0.95），单次测量不足以判定回退。

处置：
- 提交到仓库的 **`lighthouserc.js` 断言门槛不变**，CI（Linux 稳定 runner）为权威门禁；
- 「官网首页载荷精简」登记为后续优化项（见 §13.3），目标把总传输量压回 160 KiB 量级；
- **不得**用「本机跑出来 0.94 ≥ 0.9」来宣称指标无回退。

### 11.3 本机无法跑完 `lhci autorun` 的原因（环境限制，已彻底定位）

`pnpm exec lhci autorun` 在本机**确定性**失败（多次复现，非 flake）：

```
Run #1...failed! → Error: Lighthouse failed with exit code 1
Runtime error encountered: EPERM, Permission denied:
  \\?\C:\Users\Lenovo\AppData\Local\Temp\lighthouse.<随机>
  at rmSync (node:fs:1283)
  at Launcher.destroyTmp (lighthouse/node_modules/chrome-launcher/dist/chrome-launcher.js:367)
  at Launcher.kill   (…/chrome-launcher.js:349)
  at runLighthouse   (lighthouse/cli/run.js:217)
```

- 根因：Lighthouse 自带的 chrome-launcher 用 `rmSync(userDataDir, {recursive:true, force:true, maxRetries:10})` 删除自己 `mkdtemp` 出来的 Chrome profile 目录；Windows 上句柄释放慢于该重试窗口（默认 retryDelay 100ms × 10 ≈ 1s）。**审计结果其实已经生成完毕**，只是清理阶段让进程 exit 1，lhci 遂把 Run #1 判为 failed 并中止，`assert` 阶段永不执行。
- 已逐条排除并**放弃**的绕行方案（避免后人重走）：
  - 改 `TEMP` / `TMP` 指向别的目录 → 无效；
  - `collect.settings.chromeFlags` 传数组 → 被 lhci `node-runner.js:46-49` 的 `chromeFlagsAsString += ' --headless=new'` 用逗号 `toString()` 连成一个无效 flag（**该字段必须传空格拼接的字符串**，已在配置里注释说明）；
  - 用 `--cli-flags-path` JSON 传 `chromeFlags` → 无效；
  - 覆盖 `--user-data-dir` 指向可控目录 → **无效**：实测 Chrome 取**第一个** `--user-data-dir`，而 chrome-launcher 把临时目录的 flag 排在用户 flag **之前**，用户 flag 无法覆盖；
  - 降级 `--headless=new` → `--headless=old` → 无效，lhci 把 `--headless=new` 追加在最后。
- **本报告采用的取证方式**：直接调用 Lighthouse CLI（与 lhci 同口径：同一 URL、默认移动端仿真、同一组 `chromeFlags`），**报告在 `kill()` 之前已落盘**，故 3 次干净样本的分数可信；因追踪存在 flake（8 次里 5 次脏：`NO_NAVSTART`×4、`PROTOCOL_TIMEOUT`×1，会把 performance/best-practices 置 `null`），故循环采集直到攒够 3 次 `runtimeError` 为空的样本再取中位数。
- 另注：`.lighthouseci/assertion-results.json`（2026-09-15）里只有一条 `first-contentful-paint` 断言且 `passed: false`，说明旧基线是用更早的配置跑的；**当前这套 category 断言在 CI 上才是第一次被真正验证**，本节是本机首份有效数据。
- 本机环境事实：未安装独立 Chrome，Lighthouse 实际使用 Playwright 自带 chromium `ms-playwright/chromium-1243/chrome-win64/chrome.exe`。
