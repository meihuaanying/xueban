## 1. 逐项发现与处置

### ① pytest 全量失败、单跑通过（最严重）

**现象**：用户实测全量跑失败 `tests/test_account_deletion.py::test_purge_deletes_expired_accounts_with_cascade`
（`assert UUID(...) in []`），但该文件单跑 4/4 全过。

**根因**：`tests/conftest.py` 的 `clean_database` 是**函数级 autouse，只在每个用例结束
后**清库。而被外部中断的运行不会执行 teardown，**上一次留下的数据就成为下一次运行
第一个测试的输入**。所以「单跑通过」是因为单跑时前面的测试都清干净了，「全量失败」
是因为开头就踩在脏数据上——失败点（账号注销 purge）与真正的问题毫无关系。

**取证**：
- 干净库全量跑 → exit=0
- `pg_stat_user_tables` 44 张表除 `alembic_version` 外全部 0 行 ⇒ **套件完全自播种，
  会话开始清空是安全的**（如果依赖 `seed_demo_data.py` 预置数据，就不能这么清）
- 直接调新加的 `_wipe_test_database()`：脏库时 `(users=1, kps=1)` → 清完 `(0, 0)`

**修法**（`services/api/tests/conftest.py`）：
- 抽出 `_truncate_statement()`，`prepare_database` 与 `clean_database` 共用同一句 TRUNCATE
- 新增 `_wipe_test_database()`，在 `prepare_database` 迁移完成后调用（不用
  `DROP DATABASE`：迁移状态要保留）
- **清完逐表复查**：任一表仍有行就 `RuntimeError` 并点名表名——漏表通常是
  `Base.metadata` 没导入某个模型，漏了就会变成下一轮同样的幽灵污染

**验证**：**从脏库起步**连跑 4 次全量，全部 exit=0、零 FAILED、覆盖率 91.03%。

**没有采用的错法**：调整测试顺序、给这条测试加 `@pytest.mark.last`、或者干脆改成
`pytest.skip`——那都是把症状藏起来，脏库还在，下一个被踩的测试还会来。

## 3. 新增取证规范（写进报告规范，后续必须遵守）

1. **质量门一律去缓存重跑**：`pnpm exec turbo run <task> --force`，并在输出里核对
   `Cached: 0 cached`。`pnpm test` 命中 turbo 缓存时**一条用例都没跑**，却和真跑过的
   输出长得几乎一样——这是本次「报告数字不成立」的一半原因。
2. **pytest 门禁用整批跑，不用分块凑数**。此前报告写「641 passed」，那个数字来自按
   文件分块跑（整批会被外部中断），分块的累计与整批口径不同。分块只能用于**排障**，
   不能用作门禁证据。
3. **起批前查残留 pytest 进程**：`Get-CimInstance Win32_Process -Filter
   "Name='python.exe'" | Where-Object { $_.CommandLine -like "*pytest*" }`。批被 kill 后
   **必须**确认它的 python 子进程退出了——Windows 上父 shell 被杀、子进程会活下来。
4. **绝不并行跑两批 pytest**（会同抢 `xueban_test` 的 TRUNCATE 锁）。
5. **「整轮大面积 F」先看失败形态再下结论**：`assert 401` 这类跨用例认证态异常指向环境，
   `AttributeError` 之类才指向代码。本次那批 55 条 F（大量 `assert 401` +
   `test_seed_idempotent assert 641 == 0`）第一反应会被当成鉴权或数据隔离回归。
6. `ast.parse` 说文件 PARSE OK 而 pytest 报 `SyntaxError` 时，先删 `tests\__pycache__`
   ——那是陈旧 `.pyc`，不是代码坏了。
7. PowerShell `Tee-Object -FilePath` 落的日志是 **UTF-16LE**，用 `-Encoding utf8` 读会得到
   一片 U+FFFD 却不报错——读 pytest 输出前先探测 BOM。

## 4. 为什么报告里的门禁数字与实测不符（用户第 ① 项的重点）

两层掩盖叠在一起：

**第一层（测试侧）**：`clean_database` 只在用例结束后清库，被中断的运行不留清理机会，
于是脏数据变成下一次运行的输入。而「单跑某文件」永远是干净的，所以**任何按文件的
抽查都会显示通过**。这解释了「用户全量失败、agent 单跑全过」这个看似矛盾的现象。

**第二层（工具侧）**：`pnpm test` 默认吃 turbo 缓存。缓存命中时**一条用例都没执行**，
但输出格式与真跑几乎一致，只有 `Cached: 5/5` 这一行不同。不核对这一行，就会把
「上次的缓存结果」当成「这次的测试通过」写进报告。

两层叠加的后果是：报告里的门禁数字**曾经不成立，而报告本身看不出问题**。修法不是把
数字改好看，而是把隔离修对（`prepare_database` 阶段清库 + 清完逐表复查）、
把口径改对（整批连跑三次）、把取证规范改对（`--force` + 核对 `Cached`）。

> 同一类错误在 P1 期间已经犯过一次：`docs/verification/RB_P1_2026-10-03.md` 的
> §8 缺陷 17 记录过「统计脚本口径与生产取题口径不一致」——验收口径必须与生产口径
> **逐字一致**，否则统计脚本会系统性地替失败的实现背书。
